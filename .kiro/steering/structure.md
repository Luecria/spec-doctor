## Module Roles & Responsibilities

### Parser (`src/parser.ts`)
- Extract requirement blocks (R1, R2, ..., R999) and unnumbered requirements
- Extract task blocks (T1, T2, ..., T999) and unnumbered tasks
- Extract design sections (headers and content)
- Assign sequential IDs to unnumbered items in document order
- Track parse notes (warnings, encoding issues)
- Record line numbers for every structure

### Criteria (`src/criteria.ts`)
- Validate acceptance criterion format: GIVEN/WHEN/THEN (case-insensitive)
- Validate EARS patterns: Ubiquitous, Event-driven, State-driven, Unwanted, Optional
- Detect untestable criteria (e.g., "user should be happy")
- Report format validation results with reasons

### Auditors (`src/auditors.ts`)
- **RequirementsAuditor**:
  - Detect vague language (may, might, perhaps, ideally, could, should consider)
  - Validate acceptance criteria format (GIVEN/WHEN/THEN or EARS)
  - Detect duplicates via Jaccard similarity >0.90
  - Find orphaned requirements (no task references)
- **DesignAuditor**:
  - Check for data model section (vocabulary + length + structure)
  - Check for error handling section (vocabulary + length + structure)
  - Conditionally check for API contracts (only if interface surface described)
  - Flag missing or insufficient sections as Critical
- **TasksAuditor**:
  - Verify each task references at least one requirement
  - Detect oversized tasks (>5 acceptance criteria)
  - Flag missing implementation acceptance criteria
- **CrossFileAuditor**:
  - Link requirements to tasks bidirectionally
  - Flag requirement-to-task mismatches
  - Runs only if all 3 files provided

### Similarity (`src/similarity.ts`)
- Normalize text: lowercase, strip punctuation, collapse whitespace
- Tokenize by whitespace
- Compute Jaccard similarity: |intersection| / |union|
- Flag pairs with similarity >0.90 as duplicates

### Engine (`src/engine.ts`)
- Orchestrate parser, auditors, scorer
- Implement partial-file degradation: skip cross-file checks if <3 files
- List skipped checks in report with reasons
- Apply error recovery and user-friendly messages

### Scoring (`src/scoring.ts`)
- Implement diminishing deduction algorithm
- Base deductions per severity: Critical 15, High 8, Medium 3, Low 1
- Within same severity: each additional finding = 60% of previous deduction
- Minimum per-deduction: 1 point
- Floor score at 0
- Generate deduction breakdown for report

### Report (`src/report.ts`)
- Organize findings by file (requirements, design, tasks)
- Sort findings by line number within each file
- Format each finding: file, line, severity, category, quote, explanation, suggestion
- Generate JSON export: complete audit data (structure, findings, score)
- Generate Markdown export: human-readable format suitable for GitHub/email

### Drift (`src/drift.ts`) — Phase 2
- Extract ZIP files in-browser using JSZip
- Build file index with paths, types, content
- Scan code files for requirement IDs (R1, R2, ...) and task IDs (T1, T2, ...)
- Record file path, line number, context for each reference
- Generate traceability signals (not authoritative proof)
- Cap repository size at 50MB

### LLM (`src/llm.ts`) — Phase 2
- Accept OpenAI-compatible endpoint URL, API key, model name from user
- Store API key in memory only (never persistent)
- Trigger LLM review only on explicit user action
- Send spec content to user-configured endpoint
- Receive and format LLM suggestions
- Label LLM findings separately; preserve deterministic score

### UI (`src/ui.ts`)
- Render file upload/paste interface (two tabs)
- Display file metadata (names, character counts)
- Show progress indicator during audit
- Render health score with color coding (green/yellow/red)
- Display findings grouped by file/severity
- Support filtering and sorting findings
- Provide copy buttons for quotes
- Show context lines for each finding
- Render export modal (JSON/Markdown options)

### Styling (`src/style.css`)
- Global layout: flexbox/grid for responsive design
- Color scheme: accessibility-compliant (color-blind friendly)
- Typography: readable sans-serif, appropriate line-height
- Syntax highlighting for quoted spec text
- Health score color bands: green (90–100), yellow (70–89), red (<70)
- Mobile-first responsive approach

### Main (`src/main.ts`)
- Initialize DOM
- Attach event listeners to UI elements
- Start application lifecycle
- Minimal logic; delegates to UI and engine modules

## Naming & Organization Conventions

### File Naming
- **TypeScript modules**: lowercase with hyphens if multi-word (e.g., `file-parser.ts`, not `FileParser.ts`)
- **Test files**: mirror source name with `.test.ts` suffix (e.g., `parser.test.ts` tests `parser.ts`)
- **Exported functions**: camelCase (e.g., `parseRequirements()`, `detectDuplicates()`)
- **Exported interfaces**: PascalCase (e.g., `SpecFile`, `Finding`, `AuditReport`)

### Constants & Enums
- **Severity levels**: string enum or literal union: `'Critical' | 'High' | 'Medium' | 'Low'` (PascalCase values)
- **File types**: string enum: `'requirements' | 'design' | 'tasks'` (lowercase values)
- **Base deductions**: object with keys matching severity: `{ Critical: 15, High: 8, Medium: 3, Low: 1 }`

### ID Conventions
- **Requirement IDs**: `R` followed by digits (R1, R2, ..., R999); prefix-matched case-insensitively in parser
- **Task IDs**: `T` followed by digits (T1, T2, ..., T999); prefix-matched case-insensitively in parser
- **Finding IDs**: UUID or sequential number unique within audit report (for linking, not displayed to user)

### Finding Categories
- **Requirements checks**: "Vague Language", "Untestable Criteria", "Missing Acceptance Criteria", "Orphaned Requirement", "Duplicate Requirement"
- **Design checks**: "Missing Data Model", "Missing Error Handling", "Missing API Contracts", "Incomplete Documentation"
- **Tasks checks**: "Missing Requirement Reference", "Oversized Task", "Orphaned Task", "Missing Criteria"
- **Cross-file checks**: "Requirement-Task Mismatch", "Orphaned Requirement", "Orphaned Task"

### Report Organization
- **By severity first**: Critical findings listed first, then High, Medium, Low
- **By file second**: Within severity, group by source file (requirements, design, tasks)
- **By line third**: Within file, sort by line number ascending

## Fixtures Structure

### good-spec/
- **requirements.md**:
  - R1, R2, R3: well-written with complete acceptance criteria
  - All criteria in GIVEN/WHEN/THEN or EARS format
  - No vague language
  - All traced to tasks (T1, T2, T3)
  - Expected audit result: High health score (90+), no Critical/High findings

- **design.md**:
  - Clear data model section with 2+ vocabulary terms, 200+ characters, structured elements
  - Clear error handling section with vocabulary and structure
  - API contracts section with detailed interface documentation
  - Expected: No findings

- **tasks.md**:
  - T1, T2, T3: small-to-medium sized, each <5 acceptance criteria
  - Each task references R1, R2, or R3 appropriately
  - Clear, implementable scope
  - Expected: No findings

### bad-spec/
- **requirements.md**:
  - R1 with vague language: "The system should ideally handle errors gracefully"
  - R2 with untestable criterion: "The design shall be beautiful"
  - R3 orphaned (not referenced by any task)
  - R4 duplicates R1 (Jaccard similarity >0.90)
  - Expected: Multiple findings (Low, High, Medium)

- **design.md**:
  - Missing data model section
  - Error handling mentioned in one sentence only (<200 chars, no vocabulary)
  - API contracts mentioned but not specified (if interface surface exists elsewhere)
  - Expected: 2–3 Critical findings

- **tasks.md**:
  - T1 oversized: 8 acceptance criteria
  - T2 missing requirement reference
  - T3 orphaned (not linked to any requirement)
  - Expected: Multiple High/Medium findings

## Stage Verification Reports (Root)

**Location**: Project root directory  
**Naming convention**: `REPORT-<STAGE>.txt` (e.g., `REPORT-T2-PARSER.txt`, `REPORT-T345-AUDITORS.txt`)  
**Purpose**: Document verification of implementation stages during development  
**Files**: 
- `REPORT-T2-PARSER.txt`
- `REPORT-T345-AUDITORS.txt`
- `REPORT-REMEDIATION.txt`
- `REPORT-REMEDIATION-2.txt`
- `REPORT-UI.txt`
- `REPORT-DRIFT.txt`
- `REPORT-LLM.txt`

## Exported Audit Reports (Generated)

**Location**: Project root (user configurable on export)  
**Naming convention**: `spec-doctor-report.<FORMAT>` (currently without timestamp; timestamp naming deferred)  
**Formats**: `.json` or `.md`  
**Status**: Currently exports as `spec-doctor-report.json` or `spec-doctor-report.md` (timestamp in filename is deferred; tracked in spec T8)  
**Retention**: User manages cleanup; not version-controlled

## Build Artifacts Directory (`dist/`)

- **Location**: `dist/` at project root
- **Contents after `npm run build`**:
  - `index.html`: Bundled HTML with inline script tags for bundled JS
  - `assets/`: Folder containing CSS, minified JavaScript, source maps
  - Copied static files from `public/`
- **Status**: Generated on-demand; not version-controlled

## Pre-Commit & File-Save Hooks

- **typecheck-on-save.json**: Runs `npx tsc --noEmit` when `.ts` files in `src/` are saved
  - Catches type errors immediately during development
  - Prevents committing code with type violations
